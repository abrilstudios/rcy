# rcy behaviours, merged from the issues report and the PR/doc report

## 1. Behaviour table

Key to the table:

- `issues` is `rcy-issue-behaviours.md` and `PRs` is `rcy-pr-doc-behaviours.md`. The last line of each evidence cell names the source rows that were merged into the row, using each report's own row ids.
- Text in double quotes is verbatim from one of the two reports' quotations. `#N` is an issue number, `PR #N` a pull request, and a seven-character hex string a commit.
- CONFLICT marks a row where the two reports state incompatible facts about a value or about whether the behaviour shipped; both statements are kept. `Source conflict` marks a contradiction that one report records among its own sources.
- Status `implemented (issues)` means the issues report records the behaviour as implemented from issue text; that report read no Python source. `on main` comes from the PR report, which uses "main" for merged work and labels only its open and removed rows; a PR row with no label is recorded here as on main. Behaviour that was shipped and later deleted is recorded as reversed.
- `(issues only)` or `(PRs only)` in the kind column means the other report has no row for the behaviour.

## 5. Cut position and clicks

Where a cut falls:

- Slice boundaries sit at detected hit positions, at even musical divisions, or where the user puts them (DET-01, SLC-07, SLC-02). #1 says the first slice needs a marker at zero.
- `docs/breakbeat-science.md` names three ways to cut: by grid ("Chop the loop by **time**, not transients"), by hand ("Place each slice **by hand** where it sounds right"), and by loading another producer's layout ("Use **someone else's slices**"). Automatic hit detection is not one of the three. The PR report records "Chop the loop by **time**, not transients" as the reason for a decision it names grid slicing first.
- The terminal `/marker` command places a cut on the tempo grid, not on a hit (#169). Snapping a dragged marker to the nearest hit was a wish in #156 and was never built.
- No issue says whether a cut should fall before, on, or after the onset of a hit, and no issue specifies a pre-roll or look-back from a detected onset.
- On main, the docs name the detector only as "AI-based onset detection using librosa"; no hop size is named, and reading it as librosa's default would be inference (PR report). The PR report found the pattern `backtrack` once, in open PR #190, so backtracking is not on main. Two facts from outside that report's reading allowance: detection runs on the left channel only, and only onsets strictly inside L-R are kept.
- Open PR #190 would add an onset-relative rule: `--snap-onsets [MS]` moves a grid cut to 3 ms before the nearest onset when one lies within half a sixteenth, and otherwise leaves the cut and warns. The same PR adds `--grid-offset MS`, a second detector with "64-sample hop and backtracking for cutting", and cut lists whose positions are written in samples, seconds or bar.beat.sixteenth.
- PR #190 also adds the owner-approved 12-slice Amen chop as a fixture: "All 12 boundaries equal the owner-approved manifest sample for sample". The PR report calls that fixture the only scored reference for cut placement in any source it read.
- PR #190 records that the producer validation run "had to write its own onset detection, grid math, manifest builder and verification table".
- Fine placement is by ear: markers are nudged while a loop plays (#155), in 100-sample steps per the issues report (#167) and in steps of about 10 ms, 1 ms and 100 ms per the README as read by the PR report (SLC-10, CONFLICT); #73 puts chop choice with the person.
- Timing precision is the recorded reason for one playback and export pipeline: "Shifting a snare by 1 ms can kill a groove." (deleted doc `designs/playback-export-pipelines.md`).

Zero crossings:

- Zero crossings appear once in the issues. #151 "natural zero crossings inadequate" gives the reason they are not relied on: breaks with cymbals and overlapping hits have no clean crossing near the cut. No issue asks for snapping cuts to zero crossings.
- The PR report says nothing about zero crossings.

Fades:

- Clicks are handled by fades, not by moving the cut.
- Tail fade history in the issues: samples slider (#8), 5 ms default (#39), 10 ms exponential in export (#80), 2 ms exponential fixed in code (#151), 3 ms (#175).
- Fade-in at slice start appears only in #175 and #176, at 3 ms, with "3–5 ms" in the test text. #175: "Hard-cut semantics with short configurable fade-in (anti-click)".
- Fades must not move anything in time: #39 "Must not alter timing or sequencing".
- PR history: tail fade added (PR #81); "Implemented 2ms exponential fades at stream start/stop transitions" (PR #150); fades commented out (PR #152); later enabled by default at 3 ms in `config/config.json`.
- Current engine values per the PR report: fade-in 3.0 ms and tail fade 3.0 ms, exponential, with `/set release <ms>` changing the tail (README, default 3 ms). The exponential ramp is a cube, t³, a fact from a function body outside that report's reading allowance.
- The sources the PR report read disagree on the tail fade (K1): `config/config.json` says enabled, 3 ms, exponential; `docs/tui-guide.md` says the curve is "linear"; `docs/CONFIGURATION_GUIDE.md` and the `audio_utils.apply_tail_fade` defaults say disabled, 10 ms; PR #150 used 2 ms.
- The issues report counts five different fade values and no measurement in the issues; both reports class the length and curve as HUMAN.
- Whether the fade is global or per slice was never settled in the issues (#39 global only, #151 per-segment override, #175 global values only).
- The motivating failure for the engine work, from PR #149: "This causes latency + pops that destroy musical playability". c224989 gives "pops and latency during playback" as the reason tempo moved from per-segment resampling to the engine sample rate.
- The two reports conflict on whether the engine that carries the 3 ms fades is still open (#175, issues) or on main (02b4fcf, PRs).

Tails and joins:

- A slice runs to the next boundary. In MIDI export each note lasts until the next begins: #120 "Segment 1 should end exactly when segment 2 begins (minus 1 sample)"; PR #125 "Ensures each note starts exactly when the previous one ends".
- In audition a new trigger cuts the previous slice off (#175; `ring_buffer_audio.py`: "immediately replaces any currently playing audio"); there is no overlap or release tail, and the PR report says no voice overlap is promised anywhere.
- Loops join slices with no gap and sample-accurate boundaries (#176); 528cf04 made the pattern player wait for an engine event instead of sleeping, which "eliminates timing drift in loop playback".
- Zero-length segments are skipped (SLC-01).

Inference in the issues report: because the issues leave onset-relative placement unspecified and settle fade length by repeated change, a rebuild has no stated rule to copy for either; both are open parameters.
